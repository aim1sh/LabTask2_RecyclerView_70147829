1. Executive Summary & Architecture Overview

The objective of this laboratory assignment is to engineer a production-ready Android application named UOL Course Catalogue for students of the Department of Software Engineering. The application enables students to explore the BS-SE degree curriculum through a responsive, memory-optimized RecyclerView and drill down into course-specific details with one-tap faculty email dispatch.

The application is structured into two interconnected scenarios demonstrating core Android design patterns:

  • Scenario 1 (Course List Screen): Employs the Model-View-Adapter (MVA) pattern via Course, item_course.xml, CourseAdapter, and LinearLayoutManager to render a scrolling list of elevated CardView components.
  • Scenario 2 (Course Details Screen): Decouples touch dispatching via a custom OnItemClickListener inside the adapter, determines item indices using getBindingAdapterPosition(), passes structured course parameters to CourseDetailActivity via an Explicit Intent with key constants, dynamically sets screen titles with setTitle(), and triggers an Implicit Intent (ACTION_SENDTO with mailto:) protected by exception handling.

Step 5: Comparative Testing — Without setLayoutManager()

Observation from Scenario 1, Step 5: When the app is executed with rvCourses.setLayoutManager(...) commented out, the screen displays a completely blank, empty area below the catalogue header. No course cards are visible, even though 10 courses exist in memory.
Architectural Reason: The RecyclerView decouples data management from view positioning. The Adapter binds data to ViewHolder objects, but lacks spatial awareness. The LayoutManager alone possesses the logic to measure view dimensions, compute pixel coordinates, and execute the layout pass (onLayout()). Without an assigned LayoutManager, the RecyclerView cannot determine where or how to draw its children, leaving the screen blank. Once LinearLayoutManager is restored, it measures and stacks the cards in vertical sequence.

Step 2: Explicit Intent Navigation with Key Constants

In onItemClick(int position), the tapped object is accessed with courses.get(position). An explicit Intent is instantiated targeting CourseDetailActivity.class with public static final keys: 

@Override
public void onItemClick(int position) {
    Course tappedCourse = courses.get(position);

    Intent intent = new Intent(MainActivity.this, CourseDetailActivity.class);
    intent.putExtra(CourseDetailActivity.EXTRA_CODE, tappedCourse.getCode());
    intent.putExtra(CourseDetailActivity.EXTRA_TITLE, tappedCourse.getTitle());
    intent.putExtra(CourseDetailActivity.EXTRA_CREDIT_HOURS, tappedCourse.getCreditHours());
    intent.putExtra(CourseDetailActivity.EXTRA_INSTRUCTOR, tappedCourse.getInstructor());
    intent.putExtra(CourseDetailActivity.EXTRA_EMAIL, tappedCourse.getEmail());
    intent.putExtra(CourseDetailActivity.EXTRA_DESCRIPTION, tappedCourse.getDescription());

    startActivity(intent);
}

Step 4: "Email Instructor" Implicit Intent with Safe Exception Handling

A Material button triggers an implicit intent targeting dedicated email clients using ACTION_SENDTO with mailto: URI scheme. Wrapping the call in try-catch catches ActivityNotFoundException, safely displaying a Toast message without crashing: 

btnEmailInstructor.setOnClickListener(new View.OnClickListener() {
    @Override
    public void onClick(View v) {
        if (email == null || email.trim().isEmpty()) {
            Toast.makeText(CourseDetailActivity.this, "Instructor email address not available.", Toast.LENGTH_SHORT).show();
            return;
        }

        Intent emailIntent = new Intent(Intent.ACTION_SENDTO);
        emailIntent.setData(Uri.parse("mailto:" + email));
        emailIntent.putExtra(Intent.EXTRA_SUBJECT, "Query regarding course: " + code + " - " + title);

        try {
            startActivity(emailIntent);
        } catch (ActivityNotFoundException e) {
            Toast.makeText(CourseDetailActivity.this, getString(R.string.no_email_app), Toast.LENGTH_LONG).show();
        }
    }
});

6. Viva Voce Key Concepts & Technical Questions

1. Why must the inner ViewHolder class be declared static?
Declaring the ViewHolder as static prevents it from maintaining an implicit reference to its enclosing CourseAdapter instance. This avoids potential memory leaks when the Activity or RecyclerView is recycled or destroyed during configuration changes.
2. Why is getBindingAdapterPosition() preferred over getAdapterPosition()?
getAdapterPosition() was deprecated starting in Android 11 (API 30) because when multiple adapters are merged (e.g., using ConcatAdapter), the overall adapter index can conflict with the individual sub-adapter index. getBindingAdapterPosition() deterministically returns the exact position relative to the specific adapter that bound the item.
3. Why use Intent.ACTION_SENDTO with "mailto:" rather than Intent.ACTION_SEND?
ACTION_SEND is a generic data-sharing action that opens any app accepting text/streams (WhatsApp, Drive, Messages, Twitter, Bluetooth). In contrast, ACTION_SENDTO combined with a mailto: URI filter exclusively targets dedicated email applications, guaranteeing that only email clients appear in the system chooser.
4. Why is package visibility (<queries>) declared in AndroidManifest.xml?
Starting in Android 11 (API 30), Android enforces package visibility filtering for enhanced user privacy. Without declaring <intent><action android:name="android.intent.action.SENDTO"/><data android:scheme="mailto"/></intent> under <queries>, the system hides third-party email clients from intent queries, causing resolution failures.
